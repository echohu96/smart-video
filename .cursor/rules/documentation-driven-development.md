# 文档驱动开发规则

## 核心开发理念

**文档即系统，代码即实现**

- 文档是系统的真实来源（Single Source of Truth）
- 代码只是文档的实现
- 所有设计决策、架构变更、实现细节都必须记录在文档中
- 文档必须始终保持最新，与代码同步

## 文档维护规则

### 每次改动的文档记录要求

**必须记录的内容：**
1. **变更类型**：新功能、Bug 修复、重构、文档更新
2. **变更原因**：为什么需要这个改动
3. **变更内容**：具体改动了什么
4. **影响范围**：影响哪些模块、哪些文档
5. **相关文档**：需要更新哪些文档

**记录位置：**
- `CHANGELOG.md` - 记录所有变更的摘要
- 相关技术文档 - 更新具体的技术细节
- 代码注释 - 记录实现细节

### 文档更新流程

**每次代码改动后，必须：**

1. **更新 CHANGELOG.md**
   ```markdown
   ## [日期] - 变更类型
   - **变更**：简要描述
   - **原因**：为什么改动
   - **影响**：影响范围
   - **文档**：更新的文档列表
   ```

2. **更新相关技术文档**
   - 架构变更 → 更新 `docs/architecture/ARCHITECTURE.md`
   - 实现细节变更 → 更新 `docs/architecture/IMPLEMENTATION.md`
   - 设计原则变更 → 更新 `docs/architecture/DESIGN_PRINCIPLES.md`
   - 新功能 → 更新相关模块文档

3. **更新代码注释**
   - 函数/类级别的文档字符串
   - 关键逻辑的注释说明

4. **验证文档一致性**
   - 确保文档描述与代码实现一致
   - 确保所有文档链接有效
   - 确保示例代码可运行

### 文档质量标准

**文档必须：**
- ✅ 准确反映当前系统状态
- ✅ 包含足够的上下文和背景
- ✅ 提供清晰的示例和说明
- ✅ 保持结构化和可读性
- ✅ 及时更新，不过时

**文档不应：**
- ❌ 包含过时或错误的信息
- ❌ 缺少关键实现细节
- ❌ 使用模糊或歧义的表述
- ❌ 忽略重要的设计决策

## 开发工作流

### 开始新功能/修复前

1. **查阅相关文档**
   - 阅读架构文档，理解系统设计
   - 查看实现细节，了解现有实现
   - 检查设计原则，确保符合规范

2. **更新文档（如需要）**
   - 如果发现文档过时，先更新文档
   - 如果需要新功能，先在文档中设计
   - 记录设计决策和权衡

### 开发过程中

1. **代码实现**
   - 按照文档中的设计实现
   - 如果实现与文档不一致，先更新文档
   - 添加必要的代码注释

2. **同步更新文档**
   - 实现细节变更时，立即更新文档
   - 发现文档错误时，立即修正
   - 记录实现过程中的重要发现

### 完成改动后

1. **更新所有相关文档**
   - 更新 CHANGELOG.md
   - 更新技术文档
   - 更新代码注释

2. **验证文档完整性**
   - 检查所有文档链接
   - 验证示例代码
   - 确保文档与代码一致

---

**记住：文档是系统的真实来源，代码只是实现。保持文档最新是每个开发者的责任。**
